# Patchwork architecture

Patchwork is an npm-workspace modular monolith. `apps/web` renders the UI, `apps/api` owns authentication and all database-facing endpoints, `packages/contracts` shares request validation, and `packages/db` owns the Prisma schema, migrations, and PostgreSQL client factory.

```text
Browser (APP_ORIGIN; localhost:3000 by default)
  ├─ Next.js pages
  └─ /auth/* and /api/* → Next.js rewrite → Express (localhost:4000)
                                      ├─ GitHub OAuth App: identity only
                                      ├─ GitHub App: read-only repository snapshots
                                      └─ Prisma 7 adapter-pg → PostgreSQL
```

The browser uses a single origin. Express stores a SHA-256 hash of each random opaque session token in PostgreSQL and sends the raw token only as a host-only, HttpOnly, SameSite=Lax cookie. Cookies are Secure under HTTPS. POST routes verify the request origin. GitHub OAuth uses a random state value, PKCE S256, and short-lived HttpOnly transaction cookies. The GitHub access token is used to retrieve the user's profile and is not persisted.

Workspace reads and writes are scoped by `WorkspaceMember` in the API service layer. A new workspace and its owner membership are created in one transaction. Task creation checks the actor's role and confirms any assignee is a member of the same workspace. All requests are validated against shared Zod contracts.

Workspace invitations are a fourth additive migration. A GitHub username is resolved through GitHub's public user API to an immutable account ID before the owner/admin creates an invitation. The database keeps a hash of a 256-bit random invitation token, the intended account, inviter, role, expiry, and response state. Acceptance requires an authenticated session for that exact account. A workspace row lock serializes invitation acceptance, member/role changes, and task assignment checks; membership creation and invitation acceptance commit together. Owner/admin policy prevents privilege escalation and protects the last owner. The legacy `Workspace.ownerId` reference is updated when its owner is demoted or removed.

The first migration contains `User`, `Session`, `Workspace`, `WorkspaceMember`, and `Task`. The second stores one GitHub repository connection per workspace, issue/PR snapshots, and issue-event activity. The third adds reversible disconnect state, snapshot generations, and verified task-to-GitHub links. The fourth adds workspace invitations. The fifth adds `TaskActivity`. All five migrations are additive. Tasks remain native to Patchwork. Project-health findings are calculated from existing data on each request without a new table. Background sync and notifications are not implemented.

Task creation, actual field changes, and GitHub issue/PR link and unlink transitions append `TaskActivity` in the same database transaction as the mutation. Events store an actor ID, historical login and task-title snapshots, a kind, details, and timestamp. A no-op task edit does not create an event. The combined workspace activity endpoint checks membership, merges task events with the current GitHub snapshot generation, and orders by time, source, and ID. Its HMAC-authenticated cursor carries a workspace ID, connection generation, first-page time bound, and last event position. Refresh or reconnection invalidates older cursors with a reload response. Task events remain readable if GitHub data is unavailable; the response labels saved snapshot freshness separately. Task history before this event model is not backfilled.

Task updates require an `expectedRevision` digest of persisted fields. A stale form or board move receives `TASK_CHANGED` rather than silently replacing another user's edit. Task and membership services check workspace roles server-side. Workspace row locks coordinate membership, assignment, and connection changes; task-to-GitHub link/unlink transactions also take a shared connection-row lock before reading the active generation. Real PostgreSQL race testing is still an outstanding verification step.

Repository connection has a separate GitHub App user authorization flow. The callback verifies the Patchwork session, OAuth state, GitHub user ID, and repository access before saving the connection. The user access token is discarded. Manual refresh mints a short-lived installation token restricted to the selected repository, then updates metadata, issue/PR snapshots, and timeline events in a transaction. Every API read checks workspace membership; connecting, disconnecting, and refreshing require OWNER or ADMIN. Disconnect and unlink actions set timestamps rather than deleting records. Each successful refresh or reconnection advances the active snapshot generation in the same transaction as its data writes. Records absent from the new snapshot remain stored but are excluded from active reads; returning GitHub IDs update their existing rows. Active task links follow the current generation, so links from a different previously connected repository remain stored without appearing as current links.

Prisma 7 loads the database URL through `packages/db/prisma.config.ts`, generates a client into an ignored directory, and uses `@prisma/adapter-pg` at runtime. Development and test use separate PostgreSQL databases. The API integration runner checks both URLs and the databases they actually reach before running tests that write data. A successful end-to-end PostgreSQL race verification remains outstanding.

`User` owns sessions and can join many workspaces through `WorkspaceMember`. Each `Task` belongs to one workspace, has a creator and optional assignee, and can have historical `TaskActivity` and `TaskGitHubLink` rows. `WorkspaceInvitation` belongs to a workspace and targets a GitHub account ID. Each workspace has at most one `GitHubConnection`, which owns saved `GitHubItem` and `GitHubActivity` rows. Connection generations distinguish current snapshot rows from retained history. The schema and SQL migrations are kept under `packages/db/prisma/`; migrations are applied separately to development and test databases after checking the target.
